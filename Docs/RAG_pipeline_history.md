# ESG RAG 인덱스 구축 파이프라인 — 개발 히스토리 (v1 ~ v4)

> 3개 채팅 세션에 걸쳐 진행된 개발 과정을 통합 정리한 문서.
> ① 파이프라인 기반 데이터베이스 구축 및 항목 매칭 → ② 하이브리드 검색 기반 RAG 설계 및 작업 분담 → ③ 본 채팅(검증 CSV 기반 버그 수정 및 파이프라인 검증 체계 구축)
> 보고서 작성 시 "왜 이렇게 설계했는가"의 근거 자료로 활용.

## 1. v1 (최초 프로토타입)

전달받은 내용 기준 정리. 아래 문제들이 이후 v2에서 Gemini 피드백으로 발견/수정됨:

- `PyMuPDFLoader`로 페이지 전체 텍스트 추출 + pdfplumber로 표 추출을 병행 → 표 안의 텍스트가 본문 텍스트에도 중복으로 섞여 들어감
- BM25 인덱스를 pickle로만 저장, 재시작 시 불러오는 로직 없음
- `Chroma.from_documents()`를 전체 청크에 대해 한 번에 호출 → 100개사 처리 중 중단되면 처음부터 다시 시작해야 함
- Chroma 메타데이터에 `None`/`list` 타입을 그대로 넣어 적재 에러 발생

## 2. v1 → v2: Gemini 피드백 반영

| 문제 | 원인 | 수정 |
|---|---|---|
| 텍스트-표 중복 적재 | `PyMuPDFLoader`로 페이지 전체 텍스트를 뽑으면서, 표 안 글자가 깨진 채로 또 들어감 | `PyMuPDFLoader` 제거, pdfplumber 하나로 통일 → 표 바운딩박스를 제외한 텍스트만 추출 |
| 세션 재시작 시 BM25 재구축 | 원본 문서를 pickle로만 저장, 다시 불러오는 코드 없음 | 재시작 전용 로드 셀(Cell R) 추가 |
| 100개사 한 번에 처리 중 중단 시 손실 | `Chroma.from_documents()`를 전체 청크로 한 번에 호출 | 회사·문서 단위로 즉시 저장 + 체크포인트 로그(리스트 형태) |
| Chroma 적재 시 타입 에러 (추가 발견) | Chroma 메타데이터는 `None`/`list` 불허 | `None`→빈 문자열, `list`→JSON 문자열로 변환 |

## 3. v2 → v3: GPT 피드백 반영 (가장 큰 폭의 구조 변경)

| 문제 | 원인 | 수정 |
|---|---|---|
| **BM25가 메타데이터 필터를 못 받음** (핵심 구조적 결함) | `EnsembleRetriever`는 dense엔 회사 필터가 걸리지만 BM25는 전체 코퍼스를 검색 | `EnsembleRetriever` 폐기 → 검색 시점에 필터로 좁힌 부분집합에서만 BM25를 만드는 `FilteredHybridRetriever` 직접 구현 (회사별 캐싱 + RRF 결합) |
| 재실행 시 청크 중복 적재 | `add_documents`에 ID를 안 넘겨 매번 새 UUID 생성 | `chunk_id`를 Chroma `ids`로 명시 전달 |
| PDF 교체돼도 재인덱싱 안 됨 | 체크포인트가 `doc_id`만 기록, 해시 미검증 | `{doc_id: {hash, indexed_at}}` 구조로 변경 → 해시 다르면 기존 청크 삭제 후 재인덱싱 |
| 큰 표(수천 토큰)가 안 잘림 | 텍스트만 800토큰 룰 적용, 표는 무제한 | `chunk_table()` 추가 — 헤더 반복하며 토큰 기준 행 단위 분할 |
| 표 셀에 줄바꿈/파이프 있으면 마크다운 깨짐 | 셀 값 그대로 삽입 | `clean_cell()` 이스케이프 처리 |
| `indexed_at`이 청크마다 미세하게 다름 | 청크 생성마다 `datetime.now()` 호출 | 문서 단위로 1회 생성해서 재사용 |
| 전역 BM25 pickle 저장/로드 로직 불필요해짐 | BM25 구조 변경(위 항목)의 부수 효과 | Cell 8 단순화, `bm25_index.pkl` 제거 |

### v3 내 별도 논의: section_title (미완결로 남음)

- 처음엔 "지속가능경영보고서는 목차 규칙이 없어 보류"로 결정했으나, 실제 코드엔 사업보고서·지배구조보고서까지 전부 빈 값으로 박혀있던 **구현 누락**을 발견
- 정확한 문구 매칭 대신 **키워드 기반 유연 매칭**(`detect_section_title`, `SECTION_KEYWORDS`)으로 사업보고서·지배구조보고서만 우선 구현, 검증용 진단 셀(Cell Q2) 추가
- 지속가능경영보고서는 여전히 보류 상태로 v3 종료 → **v4에서도 미해결 (아래 8절 참고)**

### 환경/운영 관련 변경 (로직 변경 아닌 설정 변경, v1~v3 기간)

| 시점 | 변경 | 이유 |
|---|---|---|
| 임베딩 모델 교체 | `OpenAIEmbeddings(text-embedding-3-small)` → `GoogleGenerativeAIEmbeddings(gemini-embedding-001)` | Google AI Studio로 결제처 확정 |
| manifest 자동화 | 수동 CSV 작성 → 폴더/파일명 규칙 기반 자동 스캔(Cell 4b), 공유 링크 직접 접근 대안(Cell 4c)도 추가 | 100개사 수동 입력 비효율, 공유 폴더 구조 확정 |
| 429 RESOURCE_EXHAUSTED 대응 | 배치 분할 + 지수 백오프 재시도(`tenacity`) 추가 | 실제 실행 중 발생한 rate limit 에러 |
| 배치 크기 재조정 | 30개/3초 → 100개/1초 | 실제 계정 한도(분당 3,000요청) 확인 후 과도하게 보수적이었던 값 완화 |

## 4. v3 → v4: 검증 CSV 실측 분석 기반 수정 (본 채팅)

### 배경

v3 코드로 SK하이닉스(000660) 1개사를 실제로 인덱싱하고 CSV로 export한 뒤, **검색 이전에 추출 결과 자체를 데이터로 검증**하는 과정에서 3건의 구체적 버그를 발견. v2·v3의 수정이 "사전 설계 리뷰(Gemini/GPT 피드백)" 기반이었다면, v4는 **사후 데이터 검증(실제 export 결과 진단)** 기반이라는 점에서 성격이 다름.

| 문제 | 원인 | 수정 |
|---|---|---|
| **section_title 역행 오염** — 사업보고서 청크 1,507개 중 892개(59%)가 전부 "회사의 개요"로 찍힘 (p.6~283) | 연결재무제표 주석의 첫 항목이 항상 "1. 회사의 개요"라서, 순서 개념 없는 키워드 매칭이 이미 지나간 대분류를 다시 잡아버림 | `detect_section_title`이 `(제목, 순서인덱스)` 튜플을 반환하도록 변경, `process_document`에서 인덱스가 역행하면 무시 |
| **노이즈 청크 ~10%** — DART 뷰어 푸터(`전자공시시스템 dart.fss.or.kr Page N`), 목차 점선(`.....`) 덩어리가 그대로 인덱싱됨 | 페이지 추출 텍스트에 뷰어 UI 요소가 그대로 섞여 있었고 필터링 로직 부재 | `strip_noise_lines()`(푸터 제거), `is_toc_chunk()`(목차 덩어리 판별) 추가, 20자 미만 잔여 청크도 스킵 |
| **지속가능경영보고서 표 추출 저조** — 페이지당 표 0.65개(사업보고서 2.49개 대비 1/4 수준), 평균 길이 165자 | 선(border) 없는 디자인 표가 많아 `find_tables()` 기본(lines) 전략으로 인식 실패 | `extract_page_content`에 `doc_type` 인자 추가, sustainability_report이고 기본 전략으로 표 0개면 `text` 전략으로 재시도 |

### 재검증 결과 (v3 CSV → v4 CSV, SK하이닉스 000660 기준)

| 지표 | v3 (수정 전) | v4 (수정 후) |

| 지속가능경영보고서 표 청크 수 | 57건 | **278건** |

| 지속가능경영보고서 표 평균 길이 | 165자 | 811자 |

## 5. v4 재검증 중 새로 발견된 미해결 이슈

v4 CSV를 다시 검증하는 과정에서 아래 2건이 새로 발견됨 (아직 코드 미반영):

| 이슈 | 상세 | 상태 |
|---|---|---|
| KIND(한국거래소) 뷰어 노이즈 | 지배구조보고서에서 DART가 아닌 KIND 뷰어 특유의 헤더/푸터(`오후 X:XX ... 공시`, `https://kind.krx.co.kr/...` URL줄) 3건 발견 — 기존 DART 전용 정규식으론 안 걸림 | 우선순위 낮음, 패치 코드는 준비됨(`KIND_FOOTER_PATTERN`, `KIND_URL_LINE_PATTERN`) |
| 중복 content 청크 증가 | 58건(v3) → 71건(v4), 전체의 3.5% | 원인 미확정 (표 fallback이 같은 표를 이중 인식했을 가능성). 검색 품질에 큰 영향은 없을 것으로 판단, 후순위 |

## 6. v1부터 계속 보류 중인 항목 (v4 시점까지 미해결)

- **지속가능경영보고서 section_title**: v4에서 표 추출은 고쳤지만 섹션 제목 감지 자체는 여전히 미구현 (`SECTION_KEYWORDS`에 키 없음). v3 논의에서 이미 보류 결정된 사항이 그대로 이어짐.
- **`applicable_item_codes` / `esg_area` 필드**: 처음부터 TODO로 설계됨, 전 버전에서 계속 빈 값(`[]`, `""`). K-ESG 91항목 규칙 기반 태깅 예정이나 아직 미착수.
- **하이브리드 결합 가중치(dense:BM25) 튜닝, 리랭커(Cross-Encoder) 적용 여부**: v3에서 구조는 갖춰졌으나 파라미터 튜닝은 평가셋 확보 후로 미룸 (7절 참고).

## 7. 별도 트랙: 파이프라인 검증 프레임워크 구축 (본 채팅)

노트북 버전과는 별개로, **팀원 파이프라인과의 비교·채택 결정**을 위해 진행:

- **KRX 15개 O/X 지배구조 핵심지표 평가셋** 구축 — SK하이닉스 지배구조보고서 p.2~3에 회사가 자율공시한 "지배구조핵심지표 준수 현황" 표를 그대로 활용 (별도 라벨링 없이 100% 신뢰 가능한 정답 확보)
- **순수 Python BM25 기반 Recall@k 평가 스크립트** (`krx15_recall_eval.py`) — 외부 라이브러리·임베딩 API 의존 없이, 어떤 팀원의 export CSV든 동일 기준으로 검색 성능(Recall@5, Recall@10, MRR) 비교 가능하도록 설계
- **v4 파이프라인 자체 검증 결과**: KRX 15개 항목 전부 top-10 안에서 정답 페이지 발견 (Recall@5 = 100%, Recall@10 = 100%, MRR = 0.967)
- 한계: 형태소분석기 미적용 단순 토크나이저 기반이라 절대 수치보다는 **파이프라인 간 상대 비교**용으로 의미 있음

## 8. 운영 이슈: Chroma-on-Drive 손상 (코드 버전과 별개, 인프라 이슈)

- Google Drive에 마운트된 경로에서 Chroma 벡터스토어를 직접 조작하다 `Error loading hnsw index` 발생
- 원인: Drive FUSE 마운트의 비원자적(non-atomic) 쓰기 특성이 Chroma HNSW 인덱스의 mmap 기반 파일 구조와 상성이 나쁨
- 대응 방향: **로컬(`/content`)에서 인덱싱 → 완료 후 Drive로 복사(백업)** 패턴으로 전환 권고. 아직 노트북 본체(v4)에 정식 반영은 안 됐고, 가이드로만 전달된 상태.

## 9. (조건부/향후 계획) 100개사 스케일업 설계 — 아직 미착수

팀 내 파이프라인 채택 결정을 전제로 설계만 완료된 상태:

- **배치 자동화 자체는 이미 준비됨**: `build_manifest()`(Cell 4b)가 폴더/파일명 규칙 기반으로 전체 회사를 자동 스캔하고, `process_document`(Cell 7 루프)가 doc_id 단위 체크포인트로 이어서 처리 가능 → 테스트용 필터(`TEST_COMPANY_CODES`) 라인만 제거하면 최대 1,200건 자동 처리
- **새로 식별된 위험**: 5인이 동시에 같은 공용 Chroma DB(Drive)에 쓰기 작업을 하면 8절의 손상 사고가 필연적으로 재발
- **제안 아키텍처 (분할-병합)**:
  1. 팀원별로 담당 회사(예: 20개사)를 나눠 각자 로컬(`/content`)에 독립적으로 인덱싱
  2. 텍스트+메타데이터+**임베딩 벡터**까지 포함해 parquet로 export (재임베딩 비용 방지)
  3. 1인이 5개 parquet를 순차적으로 하나의 최종 Chroma DB에 병합 (동시 쓰기 없음)
- 상태: 코드 스니펫 수준까지 설계 완료, 정식 노트북 셀로는 아직 미작성 (파이프라인 채택 확정 시 진행 예정)

- v2·v3는 **외부 피드백(Gemini/GPT) 기반 사전 설계 리뷰**로 개선된 반면, v4는 **실제 인덱싱 결과물을 데이터로 진단**해서 발견한 버그라는 점이 방법론적으로 구분됨 → "설계 검토"와 "데이터 기반 QA"를 모두 거친 개발 프로세스였다는 점을 강조 가능
- v2→v3의 BM25 필터링 구조 결함은 **구조적 설계 문제**(고치지 않았으면 필터링된 검색 자체가 무의미했을 것)였고, v3→v4는 **구현 세부 버그**(전체 아키텍처는 정상, 특정 로직만 오류) — 문제의 성격이 다르다는 점도 서술 가능
- 7절의 검증 프레임워크는 "왜 이 파이프라인을 최종 채택했는가"의 근거 자료로 그대로 활용 가능
