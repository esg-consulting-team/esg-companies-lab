## 00. 구현 전제

> **v0.3(최초 사양서) 대비 가장 큰 차이**: 그때는 목업 JSON으로 화면만 그리는 단계였고, 지금은 **Supabase(Postgres) + FastAPI 백엔드 + React 프론트**가 실제로 돌아가는 시스템입니다. 두 회사의 K-ESG 채점 엑셀 2개, 컨설팅보고서 docx 2개에서 실제로 추출한 데이터가 DB에 들어가 있고, 화면은 전부 실 API를 호출합니다.

### 0.1 기술 스택

| 레이어 | 기술 | 위치 |
|---|---|---|
| DB | Supabase (Postgres 17 + PostgREST, RLS public-read) | 프로젝트 `qldhbfexzmsobnygewvm` |
| 백엔드 | Python 3.12 + FastAPI + httpx (Supabase REST 직접 호출) | `backend/main.py` |
| 프론트 | React 19 + Vite 5 + react-router-dom, 순수 CSS(디자인 토큰) | `frontend/src/` |
| 실행 | `back.bat`(:8000) / `front.bat`(:5173) / `all.bat`(둘 다 + 브라우저 자동오픈) | 프로젝트 루트 |
| 이전버전 비교 | `frontend-prev`(:5174, node_modules는 정션 공유) / `all_prev.bat` / `all_compare.bat`(신·구 동시 실행) | 프로젝트 루트 |

### 0.2 화면 구성 (변경 없음)

- **화면 7개**: L1 종합 현황 / L2 영역별 진단 / L3 항목 상세 / L4 비교 분석 / L5 개선 로드맵 / L6 증빙 데이터룸 / L7 리포트
- **공통 셸**: 상단 앱바 + 좌측 레일(178px) + 본문 + 우측 AI 상담 패널(300px, 접으면 40px 스트립)
- **AI 상담(F5 전체)은 아직 UI 껍데기만 구현**, 실제 응답 로직은 미구현(2차 확장 항목)

### 표시 원칙 4가지 (전 화면 공통 — 준수 여부 실측)

| # | 원칙 | 구현 상태 |

| 1 | 가채점 점수에는 항상 `가채점` 표기 | ✅ 앱바 배지로 상시 노출 |

### 5.1 근거 6필드 — 실제로는 자동 파싱

원본 데이터(`note_2026`, `solution` 컬럼)에 이미 `[판단근거] [확인근거] [감점사유] [보완 필요 증빙]`, `[현재 문제점] [개선방향] [필요근거]` 같은 대괄호 태그가 박혀 있었습니다. 백엔드에서 정규식(`\[([^\[\]]{2,22})\]`)으로 이 태그를 분리해 그대로 구조화된 필드로 내려줍니다 — 별도로 지어낸 필드가 아니라 컨설턴트가 이미 써둔 근거를 파싱만 한 것입니다.

| 필드 | 소스 |
|---|---|
| 점검기준(K-ESG 원문) | `esg_diagnostic_items.criteria_detail` |
| 판단근거 / 확인근거 / 감점사유 / 보완필요증빙 | `esg_diagnostic_scores.note_2026` 파싱 |

## 07. L5 · 개선 로드맵 — 전면 개편

v0.3은 항목별 `solution` 텍스트를 시급성별로 재분류한 것이 로드맵의 전부였습니다. **지금은 컨설팅보고서 원본의 4단계 로드맵 자체를 반영**합니다.

### 7.1 Exhibit 12 — 4개년 실행 로드맵 (신규)

- **소스**: 컨설팅보고서 `08 최종 로드맵` 장 → `esg_roadmap_stages`(8행) + `esg_roadmap_tasks`(40행, 두 회사 각 20건)
- 단계 구성: 1단계(2026)~4단계(2029), 각 단계마다 실행과제 5개씩
- 각 과제는 `관련 진단항목코드`(클릭 시 L3 이동)와 `산출물 및 지표`를 가짐
- **단계 배지 = 조인 기반 시급성 분포** (아래 7.2)
- API: `GET /api/roadmap-stages?company=`

### 7.2 로드맵 시급성 배지 — 설계 변천사 (3차 개정)

이 부분은 세 번 고쳤습니다. 다음 논의에서 참고할 수 있도록 과정을 남깁니다.

1. **원문 그대로**: `esg_roadmap_stages.urgency_level`(보고서 텍스트) 표시 → DN오토모티브 보고서엔 이 표 자체가 없어 전 단계 `null`, 배지가 안 뜸
2. **조인 + 최고값(worst-wins)**: `related_item_codes`로 `esg_diagnostic_scores.urgency`를 조인해 가장 급한 값 하나만 대표로 표시 → 두 회사 모두 즉시-시급성 항목이 워낙 많아 **전 단계가 "즉시"로 뭉개짐**
3. **(현재) 조인 + 개수 분포**: 단일값 대신 즉시/중기/장기 **개수 분포**를 계산해 L1과 동일한 `UrgencyDistribution` 컴포넌트로 표시. 보고서 원문 텍스트는 계산에서 완전히 배제하고, 있을 때만(하나마이크론) "(보고서 원문: 즉시)" 식 참고 캡션으로만 병기. DN오토모티브는 원문이 없으므로 캡션 없이 분포만 표시.

과제 카드 단위 배지(`computedUrgency`)는 여전히 단일 최고값 방식을 유지합니다(카드가 이미 개별 단위라 분포를 쓸 필요가 적음).

## 14. 알려진 제약사항 및 다음 논의 대상

새로 합류하는 팀원과 우선 논의할 만한 항목들입니다.

1. **L2 영역 4종 통합 미반영** — `domain_for()`에서 업종특화를 환경/지배구조로 흡수하고, 하나마이크론에만 "반도체특화 포함/제외" 토글을 노출하는 v0.6 결정이 아직 코드에 반영 안 됨
2. **로드맵 단계 배지의 "분포" 방식이 최선인지** — 현재는 개수 분포로 표시 중인데, 원본 보고서의 정성적 단계 라벨(즉시/즉시~중기/중기/장기)과 수치 분포가 항상 일치하지는 않음(§7.2)
3. **`esg_governance_company_values`가 전부 null** — 원본 엑셀 자체에 KRX 지배구조 세부지표(129개) 현황값이 입력되어 있지 않았음. 컨설턴트가 손으로 채울지, 이번 스코프에서 뺄지 결정 필요
4. **원단위 3개년 추이(F3-04), 감점 이력 타임라인(F2-05)** — 구조화된 시계열 데이터가 없어 미구현. docx에 텍스트로는 일부 있으나(예: 온실가스 원단위 수치) 표 형태로 추출 안 됨
5. **인증·권한(F6-05) 전무** — 지금은 링크만 알면 누구나 전체 데이터 조회 가능(Supabase RLS가 public read). 사내 배포 전 최소한의 접근 제어 필요
6. **AI 상담(F5) 전체가 미구현** — 컨텍스트 배지 UI만 있고 실제 RAG/답변 로직 없음. 2차 스코프로 명시적으로 미룬 상태

이 문서(v1.0) 작성 이후 진행된 작업입니다. §10.1의 데이터 모델 표는 처음부터 `esg_diagnostic_items`/`esg_diagnostic_scores` 정규화 스키마를 "실제 스키마"로 적어뒀지만, 실은 그날까지도 **실 Supabase DB엔 이 두 테이블이 비어 있었고**(0행) 진단 채점 데이터 84건은 여전히 구식 평면 테이블 `esg_diagnosis`에 들어 있었습니다. 코드(`backend/app/services/diagnosis.py`)도 그 평면 테이블을 그대로 조회하고 있었고요. 아래 작업으로 문서와 실제 상태를 처음으로 일치시켰습니다.

### 15.1 esg_diagnosis → 정규화 스키마 마이그레이션

- **DB**: `esg_diagnosis`의 84행(42항목×2개사)을 실제로 `esg_diagnostic_items`(42행, 항목 마스터)와 `esg_diagnostic_scores`(84행, 회사별 채점)로 이관. 두 테이블 다 PK/FK가 아예 없던 상태라 `esg_companies.id` PK, `esg_diagnostic_items.item_code` PK, `esg_diagnostic_scores`에 identity PK + FK(`company_id`→`esg_companies`, `item_code`→`esg_diagnostic_items`) + unique(`company_id, item_code`)를 새로 추가
- **백엔드**: `backend/app/services/diagnosis.py`의 `fetch_items()`/`build_item_detail()`, `backend/app/services/enrichment.py`의 `get_roadmap_plan()` 이 `esg_diagnosis` 대신 `esg_diagnostic_scores` ⋈ `esg_diagnostic_items` 조인 쿼리를 쓰도록 전환. 반환 필드명은 하위 서비스(roadmap/documents/reports)가 이미 기대하던 이름(`category_code`, `note_scoring_model` 등)에 맞춰 매핑해, 이 두 파일 밖은 건드릴 필요가 없었음
- 옛 `esg_diagnosis` 테이블은 백업용으로 삭제하지 않고 남겨둠
- `esg_score_scale`(313행)·`esg_governance_indicators`(129행)·`esg_governance_company_values`(258행)는 원본 소스 자체가 없어 이번 마이그레이션 범위에서 제외 — 여전히 0행(§14-3 참고)
